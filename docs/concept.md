# Концепція: secure-p2p-filedrop

## Задача

Програма для передачі файлів між двома ПК без статичної адреси / виділеного сервера. Типовий обсяг корисного навантаження — архіви середнього (сотні МБ) та великого (кілька ГБ) розміру.

## Принцип роботи

Передача даних відбувається напряму між клієнтами (**P2P**) — без проміжного сервера для самого файлового трафіку. Проблема "як двом клієнтам знайти й довірити одне одному" вирішується через ручну ініціалізацію сеансу поза застосунком.

Важливо розділяти дві різні речі, які не варто змішувати в одному кроці:

- **встановлення й перевірка з'єднання** — це сервісна (системна) функція: застосунок робить це сам, автоматично, щойно обидві сторони отримали ключ. Користувач тут нічого не "робить";
- **передача файлу** — це свідома дія користувача (вибрав файл, натиснув "Надіслати"). Вона можлива тільки тоді, коли з'єднання вже встановлене й перевірене сервісною функцією, але сама по собі є окремим кроком, ініційованим людиною, а не наслідком хендшейку.

### Фаза 1 — ініціалізація сеансу (хендшейк)

1. Користувач A вводить парольну фразу і генерує **хендшейк-пакет** — набір даних, що містить:
   - сіль (salt) для деривації сесійного ключа з парольної фрази;
   - ідентифікатор сесії;
   - інформацію, потрібну для встановлення з'єднання (в поточній реалізації — лише параметри деривації ключа; адресна/мережева інформація для P2P-конекту — наступний крок розробки).
2. Пакет **не містить самої парольної фрази** — тільки метадані. Відновити ключ з пакету без знання пароля неможливо.
3. Користувач A копіює пакет у буфер обміну і передає його користувачу B через **окремий захищений месенджер** (Signal, Telegram secret chat тощо) — сам застосунок не бере участі в цій передачі.
4. Користувач B вставляє отриманий хендшейк у своє поле, вводить ту саму парольну фразу — обидві сторони незалежно деривують однаковий сесійний ключ.

### Сервісна функція — встановлення й перевірка з'єднання

Автоматичний, системний крок, без участі користувача. Дві незалежні частини:

1. **Підготовка адреси** (`_start_connection_setup`, одразу при старті застосунку) — трирівнева спроба: локальна адреса → UPnP (власний роутер) → публічний STUN (лише дізнатись адресу, не хостинг). Результат іде в `host`/`port` хендшейк-пакета. Якщо все провалилось — лишається локальна LAN-адреса.
2. **Встановлення й підтвердження з'єднання** (`transport.py`, `_maybe_start_channel_establishment`) — щойно відомий спільний сесійний ключ: сторона, яка ЗГЕНЕРУВАЛА хендшейк, ще не знає адреси іншої сторони (хендшейк ділиться лише в один бік) — вона просто слухає на своєму порту; сторона, яка ОБРОБИЛА вхідний хендшейк, знає адресу й підключається сама. З'єднання підтверджується взаємним HMAC-запитом-відповіддю (ключ ніколи не передається по мережі) — якщо ключі не збігаються (одруківка в паролі, пошкоджений хендшейк), з'єднання явно позначається як провалене, і користувачу пропонується звірити короткий **код підтвердження ключа** (перші 8 символів SHA-256 від ключа) голосом/текстом через месенджер.

Немає relay/TURN-фолбеку навмисно (див. "Принципове архітектурне обмеження" нижче) — якщо обидві сторони недосяжні напряму (symmetric NAT/CGNAT з обох боків без UPnP), з'єднання не встановиться.

### Фаза 2 — вибір і підготовка даних (реалізовано частково)

- Вибір окремого файлу — напряму, без додаткової обробки.
- Вибір каталогу — показується дерево його вмісту (розмір кожного елемента, підкаталоги розгортаються ліниво), кожен елемент з чекбоксом (усе позначено за замовчуванням). Кнопка "Запакувати обране" пакує лише позначені файли в ZIP, складений у технічну підпапку в корені самого обраного каталогу (не в системний temp) — ця підпапка виключена зі сканування/показу дерева, щоб не потрапити в себе саму при повторному пакуванні.
- Може відбуватись у будь-який момент, незалежно від стану з'єднання.

### Фаза 3 — передача файлів: дія користувача

Явна дія користувача (кнопка "Надіслати", активна лише коли сервісна функція вище вже підтвердила, що з'єднання встановлене й ключі збігаються). Сам транспорт даних (`transport.py`) — прямий TCP-канал, кожен файл шифрується AES-256-CTR сесійним ключем із Фази 1 (окремий nonce на файл), цілісність перевіряється SHA-256 після прийому кожного файлу. Сторона може приймати кілька послідовних передач за сеанс (одна й та сама перевірена сесія).

## Вимоги й обмеження

- **Мінімум залежностей**: реалізація спирається на стандартну бібліотеку Python, за одним свідомим винятком — `pyzipper` (AES-шифрування архівів, детальніше нижче). Кросплатформенність — Windows/macOS/Linux, за умови Python зі зібраним Tk.
- Захист даних забезпечується або на рівні архіву (AES-128/256, опційно), або на рівні транспортного каналу (шифрування сесійним ключем) — користувач сам обирає рівень при ініціалізації передачі, включно з варіантом "передача у відкриту" (нульова безпека, свідомий вибір користувача).

## Відомі технічні компроміси (зафіксовано в коді)

1. ~~**Деривація ключа** зараз реалізована як ручний ланцюжок `SHA-256(SHA-256(...))`~~ — **вирішено**: перехід на `hashlib.pbkdf2_hmac('sha256', ...)` виконано, додаткових залежностей не додав.
2. ~~**Шифрування архівів**: стандартний модуль `zipfile` не вміє створювати архіви з сучасним AES-шифруванням~~ — **вирішено**: додано `pyzipper` (`requirements.txt`) — єдина зовнішня залежність проєкту, свідомий виняток із "мінімум залежностей". Користувач обирає рівень при ініціалізації передачі (`exchange.EncryptionLevel`): без шифрування (відкритий ZIP, нульова безпека), AES-128 або AES-256; паролем архіву слугує вже деривований сесійний ключ із Фази 1 (не потребує окремого обміну паролем). Стиснення (`ZIP_DEFLATED`/`ZIP_STORED`) — окрема незалежна настройка.

## Поточний стан реалізації

Готово: GUI для генерації/обробки хендшейку (деривація ключа через PBKDF2-HMAC, код підтвердження, вибір файлу/каталогу, підготовка ZIP-архіву для каталогів, вибір AES-128/256/без шифрування та стиснення/без при пакуванні), CLI-параметри `--pswd`/`-p` (попереднє заповнення пароля) та `--snd-dir` (попередній вибір каталогу для передачі), мережевий компонент хендшейку (`host`/`port`), дворівнева модель налаштування з'єднання UPnP → публічний STUN (`nat_traversal.py`, `stun_client.py`; якщо обидва не вдались — лишається локальна LAN-адреса), сам P2P-транспортний шар (`transport.py`: встановлення з'єднання, взаємне HMAC-підтвердження ключа, передача файлів AES-256-CTR з перевіркою SHA-256), вкладка "Консоль / Лог" для діагностики, вкладка "Профіль" — локальний конфіг користувача (`local_config.py`): ідентифікатор клієнта, дефолтні каталоги вхідних/вихідних файлів, редаговані в рантаймі й збережувані окремою кнопкою в `~/.secure_p2p_filedrop/config.json`.

Відомі обмеження (не блокують базове використання): без індикатора прогресу передачі у GUI (лише статус-рядок), без можливості скасувати передачу чи відновити перервану, без `bin/`-скриптів параметра для передачі паролю (лише `--pswd`).

**Принципове архітектурне обмеження**: ніколи не розробляти й не хостити власний зовнішній компонент інфраструктури (свій relay/TURN-сервер, свій сервер сигналізації тощо) — саме такого хостингу проєкт свідомо уникає (реальний трафік, реальна пропускна здатність, обслуговування, і, що іронічно, знову єдина точка відмови для інструменту, задуманого як P2P). Використання вже готового, безкоштовного, публічного сервісу, що не потребує розробки чи хостингу з боку користувача, — **інша річ і дозволене**: публічний STUN (лише дізнатись власну адресу, без передачі файлових даних) — прийнятний другий рівень спроби з'єднання (вище). Обмін мережевою інформацією (адреси, порти) все одно відбувається виключно через уже наявний канал хендшейку (месенджер); NAT-специфічні дії — це або розмова з власним роутером користувача (UPnP/NAT-PMP/PCP), або ручний проброс порту користувачем, або (як крайній, легкий випадок) запит до публічного STUN. Relay/TURN (як власний, так і сторонній платний) — виключено назавжди, це і є той самий заборонений "хостинг".
