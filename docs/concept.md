# Концепція: secure-p2p-filedrop

## Задача

Передача файлів між двома ПК без статичної адреси/виділеного сервера. Типовий обсяг — сотні МБ – кілька ГБ.

## Принцип роботи

P2P — без проміжного сервера для файлового трафіку. Два клієнти знаходять і довіряють одне одному через ручну ініціалізацію сеансу поза застосунком.

Дві окремі речі:

- **встановлення й перевірка з'єднання** — сервісна функція, автоматична, без участі користувача;
- **передача файлу** — свідома дія користувача (вибір файлу, "Надіслати"), можлива лише після підтвердженого з'єднання.

### Фаза 1 — ініціалізація сеансу (хендшейк)

1. Користувач A вводить парольну фразу, генерує **хендшейк-пакет**: сіль для деривації ключа, ID сесії, дані для з'єднання (host/port; адресна інформація — наступний крок розробки).
2. Пакет не містить парольної фрази — лише метадані. Ключ з пакету без пароля не відновити.
3. A копіює пакет і передає B через окремий захищений месенджер (Signal, Telegram secret chat тощо) — застосунок у цій передачі участі не бере.
4. B вставляє хендшейк, вводить ту саму фразу — обидві сторони незалежно деривують однаковий сесійний ключ.

### Сервісна функція — встановлення й перевірка з'єднання

Автоматично, без участі користувача:

1. **Підготовка адреси** (`_start_connection_setup`, при старті) — локальна адреса → UPnP → публічний STUN (лише дізнатись адресу). Результат — у `host`/`port` пакета; якщо все провалилось — локальна LAN-адреса.
2. **Встановлення й підтвердження** (`transport.py`, `_maybe_start_channel_establishment`) — сторона, що ЗГЕНЕРУВАЛА хендшейк, ще не знає адреси іншої й слухає на своєму порту; сторона, що ОБРОБИЛА вхідний хендшейк, знає адресу й підключається сама. Підтвердження — взаємний HMAC-запит-відповідь (ключ мережею не йде); розбіжність ключів (одруківка в паролі, пошкоджений хендшейк) — з'єднання позначається провальним, пропонується звірити **код підтвердження ключа** (перші 8 символів SHA-256 ключа) голосом/текстом.

Немає relay/TURN-фолбеку навмисно (див. "Принципове архітектурне обмеження" нижче) — обидві сторони за суворим NAT/CGNAT без UPnP → з'єднання не встановиться.

### Фаза 2 — вибір і підготовка даних (частково)

- Файл — напряму, без обробки.
- Каталог — дерево вмісту (розмір, лінива підвантаження підкаталогів), чекбокси (усе позначено за замовчуванням). "Запакувати обране" пакує позначене в ZIP у технічну підпапку кореня обраного каталогу (не temp) — підпапка виключена зі сканування, щоб не запакувати саму себе.
- Можливо в будь-який момент, незалежно від стану з'єднання.

### Фаза 3 — передача файлів: дія користувача

Кнопка "Надіслати" активна лише після підтвердженого з'єднання. Транспорт (`transport.py`) — прямий TCP, AES-256-CTR сесійним ключем (окремий nonce на файл), цілісність — SHA-256 після прийому кожного файлу. Один підтверджений канал приймає кілька передач за сеанс.

## Вимоги й обмеження

- **Мінімум залежностей**: стандартна бібліотека + свідомий виняток `pyzipper` (AES архівів) з транзитивною `pycryptodomex` (її ж напряму використовує `transport.py` для AES-256-CTR — нового пакета це не додає). Кросплатформенність: Windows/macOS/Linux, Python зі зібраним Tk.
- Захист даних — на рівні архіву (AES-128/256, опційно) і/або каналу (сесійний ключ); користувач сам обирає рівень, включно з "передача у відкриту" (нульова безпека, свідомий вибір).

## Безпека — обмеження та гарантії

Гарантує:

- Вміст завжди шифрується перед мережею: AES-256-CTR на рівні каналу + опційно AES-128/256 на рівні архіву. Сесійний ключ мережею не йде — лише деривується (PBKDF2-HMAC-SHA256, 600 000 ітерацій) і підтверджується взаємним HMAC.
- Хендшейк-пакет не розкриває ключ, навіть перехоплений.
- Цілісність файлу — SHA-256 після прийому; розбіжність → файл видаляється.

НЕ гарантує (свідомі межі, не недогляди):

- **Без TLS**: ім'я/розмір/checksum кожного файлу йдуть у відкритому JSON-заголовку — видимі пасивному спостерігачу. Прихований лише вміст.
- **Без relay/TURN**: обидві сторони за суворим NAT/CGNAT без UPnP → передача неможлива.
- **Безпека = сила парольної фрази**: PBKDF2 (600k ітерацій) підвищує вартість перебору, не рятує слабку фразу. Кнопка "Згенерувати" (`secrets.token_urlsafe`) — рекомендований спосіб уникнути ризику.
- **Без перевірки особи поза паролем**: підтверджується лише "той самий пароль", не "та сама людина" — відповідальність довіреного каналу (месенджер) + звірка коду голосом.
- **Свіжа сіль на сеанс, без класичної forward secrecy**: новий хендшейк → нова сіль → новий ключ, компрометація одного сеансу не розкриває інші. Але компрометація самої парольної фрази дозволяє дерivувати ключ будь-якого сеансу, чий хендшейк-пакет теж потрапив атакуючому.

## Відомі технічні компроміси (зафіксовано в коді)

1. ~~Ручна деривація `SHA-256(SHA-256(...))`~~ — вирішено: `hashlib.pbkdf2_hmac`, без нових залежностей.
2. ~~`zipfile` не вміє AES~~ — вирішено: `pyzipper` (єдина зовнішня залежність, свідомий виняток). Рівень обирається при ініціалізації передачі (`exchange.EncryptionLevel`): без шифрування / AES-128 / AES-256; пароль архіву = сесійний ключ (без окремого обміну). Стиснення (`ZIP_DEFLATED`/`ZIP_STORED`) — незалежна настройка.

## Поточний стан реалізації

Готово: GUI хендшейку (PBKDF2, код підтвердження, генерація фрази, вибір файлу/каталогу, ZIP з AES-128/256/без і стиснення), CLI `--pswd`/`-p`/`--snd-dir`, мережевий хендшейк (host/port), UPnP → STUN → LAN-only, транспорт (з'єднання, HMAC-підтвердження, передача AES-256-CTR + SHA-256, прогрес-бар), вкладки "Консоль/Лог", "Довідка", "Профіль" (client_id, каталоги вхідних/вихідних, `~/.secure_p2p_filedrop/config.json`).

Відомі обмеження: без скасування/відновлення передачі, без параметра пароля в bin/-скриптах (лише `--pswd`).

**Принципове архітектурне обмеження**: ніколи не розробляти й не хостити власний зовнішній компонент інфраструктури (relay/TURN, сервер сигналізації) — це саме той хостинг (трафік, обслуговування, єдина точка відмови), якого проєкт свідомо уникає. Готовий безкоштовний публічний сервіс без розробки/хостингу з боку користувача — дозволено: публічний STUN (лише власна адреса) — прийнятний другий рівень. Мережева інформація йде тільки через канал хендшейку (месенджер); NAT-дії — власний роутер (UPnP/NAT-PMP/PCP), ручний проброс порту, або публічний STUN. Relay/TURN (свій чи сторонній) — виключено назавжди.
