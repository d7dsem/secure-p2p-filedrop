# Концепція: secure-p2p-filedrop

## Задача

Програма для передачі файлів між двома ПК без статичної адреси / виділеного сервера. Типовий обсяг корисного навантаження — архіви середнього (сотні МБ) та великого (кілька ГБ) розміру.

## Принцип роботи

Передача даних відбувається напряму між клієнтами (**P2P**) — без проміжного сервера для самого файлового трафіку. Проблема "як двом клієнтам знайти й довірити одне одному" вирішується через ручну ініціалізацію сеансу поза застосунком.

Важливо розділяти дві різні речі, які не варто змішувати в одному кроці:

- **встановлення й перевірка з'єднання** — це сервісна (системна) функція: застосунок робить це сам, автоматично, щойно обидві сторони отримали ключ. Користувач тут нічого не "робить";
- **передача файлу** — це свідома дія користувача (вибрав файл, натиснув "Надіслати"). Вона можлива тільки тоді, коли з'єднання вже встановлене й перевірене сервісною функцією, але сама по собі є окремим кроком, ініційованим людиною, а не наслідком хендшейку.

### Фаза 1 — ініціалізація сеансу (хендшейк)

1. Користувач A вводить парольну фразу і генерує **хендшейк-пакет** — набір даних, що містить:
   - сіль (salt) для деривації сесійного ключа з парольної фрази;
   - ідентифікатор сесії;
   - інформацію, потрібну для встановлення з'єднання (в поточній реалізації — лише параметри деривації ключа; адресна/мережева інформація для P2P-конекту — наступний крок розробки).
2. Пакет **не містить самої парольної фрази** — тільки метадані. Відновити ключ з пакету без знання пароля неможливо.
3. Користувач A копіює пакет у буфер обміну і передає його користувачу B через **окремий захищений месенджер** (Signal, Telegram secret chat тощо) — сам застосунок не бере участі в цій передачі.
4. Користувач B вставляє отриманий хендшейк у своє поле, вводить ту саму парольну фразу — обидві сторони незалежно деривують однаковий сесійний ключ.

### Сервісна функція — встановлення й перевірка з'єднання (ще не реалізовано)

Автоматичний, системний крок, що виконується застосунком одразу після Фази 1, без участі користувача:

1. Застосунок намагається встановити P2P-з'єднання з іншою стороною й перевірити, що сесійні ключі обох сторін справді збігаються (через тестовий обмін даними, зашифрованими цим ключем), за трирівневою послідовністю спроб (без участі користувача, крок обирається автоматично):
   1. **Локально, без жодної третьої сторони**: пряме з'єднання через адресу з хендшейку — локальна адреса або порт, прокинутий через власний роутер (UPnP/NAT-PMP чи ручний проброс, див. нижче).
   2. **Якщо не спрацювало — публічний STUN-сервер**: застосунок дізнається свою публічну адресу:порт через уже готовий, безкоштовний, публічний сервіс (не власна інфраструктура — нічого розробляти чи хостити не треба), обмінюється цією адресою через уже наявний канал хендшейку і пробує пряме з'єднання ще раз.
   3. **Якщо і це не спрацювало** — P2P у цій мережі неможливий (типово: symmetric NAT/CGNAT, суворий корпоративний фаєрвол). Жодного relay/TURN-фолбеку немає навмисно (див. "Принципове архітектурне обмеження" нижче) — це кінцева відмова.
2. Якщо перевірка проходить успішно (на будь-якому з перших двох рівнів) — з'єднання позначається як "готове", і користувачу стає доступна дія передачі файлу (Фаза 3).
3. Якщо всі рівні провалились — застосунок явно повідомляє про відмову й пропонує **діагностику**: звірити короткий **код підтвердження ключа** (перші 8 символів SHA-256 від ключа) голосом або текстом через месенджер. Код безпечно передавати відкрито — з нього неможливо відновити сам ключ. Збіг/розбіжність кодів показує, чи проблема в ключах (одруківка в паролі, пошкоджений хендшейк), чи суто мережева (немає способу пробитись через NAT без relay).

### Фаза 2 — вибір і підготовка даних (реалізовано частково)

- Вибір окремого файлу — напряму, без додаткової обробки.
- Вибір каталогу — показується дерево його вмісту (розмір кожного елемента, підкаталоги розгортаються ліниво), кожен елемент з чекбоксом (усе позначено за замовчуванням). Кнопка "Запакувати обране" пакує лише позначені файли в ZIP, складений у технічну підпапку в корені самого обраного каталогу (не в системний temp) — ця підпапка виключена зі сканування/показу дерева, щоб не потрапити в себе саму при повторному пакуванні.
- Може відбуватись у будь-який момент, незалежно від стану з'єднання.

### Фаза 3 — передача файлів: дія користувача (ще не реалізовано)

Явна дія користувача (наприклад, кнопка "Надіслати") — доступна лише коли сервісна функція вище вже підтвердила, що з'єднання встановлене й ключі збігаються. Сам транспорт даних (прямий P2P-канал, зашифрований сесійним ключем із Фази 1) — наступний етап розробки.

## Вимоги й обмеження

- **Мінімум залежностей**: реалізація спирається лише на стандартну бібліотеку Python (`tkinter`, `hashlib`, `json`, `base64`, `secrets`, `zipfile`, `os`, `tempfile`). Кросплатформенність — Windows/macOS/Linux, за умови Python зі зібраним Tk.
- Захист даних забезпечується на рівні транспортного каналу (шифрування сесійним ключем), а не обов'язково на рівні архіву — це свідомий компроміс заради відсутності зовнішніх залежностей (детальніше нижче).

## Відомі технічні компроміси (зафіксовано в коді)

1. ~~**Деривація ключа** зараз реалізована як ручний ланцюжок `SHA-256(SHA-256(...))`~~ — **вирішено**: перехід на `hashlib.pbkdf2_hmac('sha256', ...)` виконано, додаткових залежностей не додав.
2. **Шифрування архівів**: стандартний модуль `zipfile` не вміє створювати архіви з сучасним AES-шифруванням (лише читати legacy ZipCrypto). Два шляхи для реального захисту:
   - додати одну зовнішню залежність (`pyzipper`, підтримує AES-256 для ZIP);
   - не шифрувати архів, а шифрувати вже встановлений транспортний канал — тоді архів можна лишити без пароля, бо захист забезпечується на рівні каналу. Це варіант, що не порушує вимогу "мінімум залежностей".

## Поточний стан реалізації

Готово: GUI для генерації/обробки хендшейку (деривація ключа через PBKDF2-HMAC, код підтвердження, вибір файлу/каталогу, підготовка ZIP-архіву для каталогів), CLI-параметр `--pswd`/`-p` для попереднього заповнення пароля, мережевий компонент хендшейку (`host`/`port`), дворівнева модель налаштування з'єднання UPnP → публічний STUN (`nat_traversal.py`, `stun_client.py`; якщо обидва не вдались — лишається локальна LAN-адреса), вкладка "Консоль / Лог" для діагностики, вкладка "Профіль" — локальний конфіг користувача (`local_config.py`): ідентифікатор клієнта, дефолтні каталоги вхідних/вихідних файлів, редаговані в рантаймі й збережувані окремою кнопкою в `~/.secure_p2p_filedrop/config.json`.

Не реалізовано: сам P2P-транспортний шар (встановлення з'єднання між клієнтами й передача файлів). Це головний наступний крок розробки.

**Принципове архітектурне обмеження**: ніколи не розробляти й не хостити власний зовнішній компонент інфраструктури (свій relay/TURN-сервер, свій сервер сигналізації тощо) — саме такого хостингу проєкт свідомо уникає (реальний трафік, реальна пропускна здатність, обслуговування, і, що іронічно, знову єдина точка відмови для інструменту, задуманого як P2P). Використання вже готового, безкоштовного, публічного сервісу, що не потребує розробки чи хостингу з боку користувача, — **інша річ і дозволене**: публічний STUN (лише дізнатись власну адресу, без передачі файлових даних) — прийнятний другий рівень спроби з'єднання (вище). Обмін мережевою інформацією (адреси, порти) все одно відбувається виключно через уже наявний канал хендшейку (месенджер); NAT-специфічні дії — це або розмова з власним роутером користувача (UPnP/NAT-PMP/PCP), або ручний проброс порту користувачем, або (як крайній, легкий випадок) запит до публічного STUN. Relay/TURN (як власний, так і сторонній платний) — виключено назавжди, це і є той самий заборонений "хостинг".
