# Чіт-шит: ручне тестування на одному ПК

Два інстанси застосунку в одному Windows-сеансі, без другого фізичного ПК.

## 1. Запуск двох інстансів

Два термінали (з кореня репозиторію):

```
python src/secure_file_drop_entry.py --pswd shared-pass
python src/secure_file_drop_entry.py --pswd shared-pass --port 52074
```

Або через VS Code: два готові launch-конфіги ("Python: Secure File Drop (GUI)" і "...- B (port 52074)") — F5/Run and Debug, обидва одночасно.

- Парольна фраза — **однакова** в обох (`--pswd` лише щоб не вводити вручну щоразу).
- Замість `--pswd` можна натиснути кнопку "Згенерувати" в одному вікні, а фразу скопіювати руками в друге (реалістичніше — так, як робитимуть реальні користувачі).
- `--snd-dir <шлях>` — одразу обрати каталог для передачі в тому інстансі, який надсилатиме.
- `--port <номер>` — одразу заповнити поле "Порт" (див. п.2).

## 2. Порт — ОБОВ'ЯЗКОВО різний, і виставляти ДО генерації/обробки хендшейку

Обидва інстанси на одній машині — однаковий порт викличе "порт зайнятий" (`transport.py`, bind-помилка) в тому, хто слухає другим.

- Найпростіше — `--port` при запуску (див. п.1), тоді поле взагалі не чіпати руками.
- Якщо міняти порт (чи парольну фразу, чи ітерації) вручну в GUI ПІСЛЯ того, як хендшейк уже згенеровано/оброблено — застосунок сам скине поточний хендшейк/канал і покаже статус "Параметри змінено..." (це виправлений реальний баг: раніше зміна мовчки нічого не міняла в уже запущеному каналі). Це нормально — просто згенеруйте/обробіть хендшейк заново.

## 3. Профіль — окремі каталоги вхідних файлів (щоб не плутати, хто що отримав)

За замовчуванням обидва інстанси на одному ПК пишуть отримані файли в ТОЙ САМИЙ `~/.secure_p2p_filedrop/...` (спільний `HOME`). Щоб отримані файли не змішувались в одному каталозі:

- Вікно B → вкладка "Профіль" → "Вхідні файли" → "Обрати..." → окремий тестовий каталог → "Зберегти профіль".
- (Альтернатива для більшої ізоляції — окремий `HOME`/`USERPROFILE` на процес перед запуском, як у `tests/test_transport.py`-стилі E2E-скриптах; для ручного тесту зазвичай досить лише каталогу вхідних файлів.)

## 4. Порядок дій — хендшейк (Фаза 1)

1. Вікно A: "Згенерувати хендшейк".
2. Вікно A: "Скопіювати в буфер" (або виділити текст мишею й Ctrl+C — обидва варіанти працюють).
3. Вікно B: "Вставити з буфера" (надійніше за Ctrl+V/праву кнопку — Text-віджет не має штатного меню "Вставити") → "Обробити вхідний хендшейк".
4. Звірити "Код підтвердження" в обох вікнах — мають **збігатись** (8 hex-символів).
5. Зачекати на секцію "Канал передачі" в обох вікнах — статус має дійти до "Підтверджено — канал готовий до передачі" (кілька секунд, залежить від мережі).

Додатково — "Перевірити канал" (кнопка під статусом каналу): швидка перевірка, що канал реально живий (ping/pong), без вибору/пакування файлів; статус внизу вікна покаже "канал працює" за кілька секунд. Корисно діагностувати "передача не спрацювала" окремо від "канал взагалі не встановився".

## 5. Порядок дій — передача файлу (Фаза 3)

1. Вікно A (те, що надсилає): "Обрати файл..." або "Обрати каталог..." (якщо не передано через `--snd-dir`).
2. Для каталогу: за потреби зняти позначки з непотрібного, обрати архів/як є, стиснення, рівень шифрування.
3. "Ініціалізувати передачу" — **готує** `transfer_payload` (Фаза 2, concept.md): якщо обрано "запакувати в архів", тут реально створюється ZIP (зі стисненням/шифруванням за налаштуваннями); якщо "як є" — просто фіксується список файлів. Нічого ще не йде в мережу; можна робити будь-коли, незалежно від стану каналу.
4. "Надіслати" — **передає** вже підготовлений `transfer_payload` через транспортний канал (Фаза 3). Активна лише коли канал підтверджено (крок 5 вище) І крок 3 вже виконано.
5. Стежити за прогрес-баром під кнопками — росте по мірі надсилання.
6. Вікно B: перевірити отримане у своєму каталозі "Вхідні файли" (Профіль).
7. Для перевірки зворотного напрямку — повторити кроки 1-5 у вікні B (той самий підтверджений канал приймає кілька передач за сеанс, новий хендшейк не потрібен).

## Типові проблеми

- **"Не вдалось встановити з'єднання" одразу (не за 300с)** — порт зайнятий (див. п.2), повідомлення тепер конкретне.
- **Канал не підтверджується довго / ніколи** — статус "Канал передачі" тепер сам показує адресу й секунди очікування (`(Nс)`), і одразу пише в лог попередження, якщо адреса іншої сторони публічна (ймовірний NAT hairpin — обидва інстанси за одним роутером). Якщо застрягло — вимкніть на хвилину інтернет або дочекайтесь, поки обидва рівні (UPnP, STUN) провалляться й застосунок відкотиться на LAN-only (реальну локальну адресу) — для однієї машини цього достатньо.
- **Коди підтвердження НЕ збігаються** — різна парольна фраза (одруківка) або зіпсований хендшейк при копіюванні.
- **Кнопка "Надіслати" неактивна** — або канал ще не підтверджено (крок 5 п.4 вище), або не натиснуто "Ініціалізувати передачу".

## Автоматичні тести (без ручного GUI)

```
bin/run-tests          # Linux/macOS
bin\run-tests.bat       # Windows
```

`tests/test_transport.py` іноді флейкає під навантаженням (`KeyError`/`WinError 10053`) — відомий артефакт тестового сетапу (обидві сторони одночасно й слухають, і підключаються — у реальному застосунку так не буває), не production-баг. Деталі: `docs/testing.md`.
