# Context dump: secure-p2p-filedrop

Швидкий вхід у проєкт. Деталі — за посиланнями, тут лише те, чого немає в інших доках.

## Огляд

Desktop GUI (Tkinter) для P2P передачі файлів між двома ПК без виділеного сервера. Дві сторони узгоджують сесійний ключ через хендшейк-пакет, переданий поза застосунком (месенджер), встановлюють підтверджений TCP-канал (UPnP → STUN → LAN fallback) і передають файли з AES-256-CTR шифруванням каналу + опційним AES архіву. Деталі протоколу й безпеки — [concept.md](concept.md).

## Життєвий цикл: хендшейк → канал → передача

Функції — `src/appearance.py` (GUI-стан, клас `SecureFileClientApp`) і `src/transport.py` (мережа).

1. **Хендшейк** (Фаза 1). Кнопка «Згенерувати» → `on_generate_handshake()`: деривує `local_key` (`derive_key`, PBKDF2), будує пакет (`build_handshake_packet`), копіює текст у буфер, показує код підтвердження. Кнопка «Вставити хендшейк» (або Ctrl+V) → `on_paste_handshake()` → `on_process_incoming()`: парсить пакет, деривує `peer_key` тією ж фразою. Один сеанс = одна роль: `local_key` і `peer_key` ніколи не встановлені одночасно (`_session_key()` без пріоритету).
2. **Встановлення каналу** (сервісна функція, автоматично). `_maybe_start_channel_establishment()` викликається одразу після кроку 1 і запускає `_channel_establish_worker()` у фоновому потоці: сторона, що згенерувала хендшейк (не знає адреси іншої), слухає; сторона, що обробила чужий (знає `peer_host`/`peer_port`) — конектиться; обидва режими — усередині `transport.establish_connection()`.
3. **Підтвердження ключа**. `transport.verify_channel()` — взаємний HMAC challenge-response, ключ мережею не йде. Збіг → `channel_verified=True`, статус «Підтверджено». Розбіжність (одруківка в фразі) → `_handle_verification_mismatch()`: діалог із полем для виправленої фрази на обох сторонах; повтор на тому самому хендшейку (`_retry_after_mismatch`) — MINE переводить ключ із тими самими salt/sid і знову слухає, PEER переобробляє збережений текст і знову конектиться. Обрив/таймаут під час підтвердження — `connection_failed`, без діалогу.
4. **Передача файлів** (Фаза 3, свідома дія, будь-яка сторона, у будь-який момент після кроку 3). «Обрати файл/каталог» → «Ініціалізувати передачу» (`on_initiate_transfer()`, готує payload/ZIP, мережі ще не чіпає) → «Надіслати» (`on_send_files()` → `transport.send_files()`, AES-256-CTR, окремий nonce на файл). Приймач: `_receive_worker` у циклі викликає `transport.receive_files()` — один канал приймає кілька передач за сеанс, у будь-який бік.

Повторне натискання «Згенерувати»/«Вставити хендшейк» при вже активному сеансі → `_confirm_reset_if_needed()` → діалог «Почати новий сеанс?»; згода скидає `local_key`/`peer_key`/канал/epoch (`_reset_session_state()`), відмова — нічого не змінює.

## Типовий флоу двох користувачів

- **A** (ініціює): вводить парольну фразу → «Згенерувати» (пакет одразу в буфері) → вставляє в месенджер, надсилає B → чекає (статус тікає, `(Nс)`).
- **B**: вводить ту саму фразу → копіює отримане з месенджера → «Вставити хендшейк» → застосунок сам конектиться до A.
- Обидві сторони бачать код підтвердження ключа (перші 8 символів SHA-256 ключа) — автоматично звірений через HMAC; якщо коди не збігаються, в обох з'являється діалог виправлення фрази — обидві вводять правильну й тиснуть OK, хендшейк повторно пересилати не треба.
- Після «Підтверджено — канал готовий» — файли може надсилати **будь-яка** сторона, в обидва боки, без нового хендшейку.
- Один сеанс = одна роль: повторний клік по «Згенерувати»/«Вставити» під час активного сеансу питає підтвердження нового сеансу (діалог), а не тихо ламає стан.

## Поточний стан (з concept.md)

Готово: GUI хендшейку, CLI-параметри `--pswd/-p/--snd-dir/--port`, мережевий хендшейк, UPnP → STUN → LAN-only fallback, транспорт (з'єднання, HMAC-підтвердження, AES-256-CTR передача + SHA-256 цілісність, прогрес-бар), вкладки Консоль/Лог, Довідка, Профіль.

Не готово / свідомо обмежено: без скасування/відновлення передачі, без пароля в bin-скриптах (лише `--pswd`), без TLS (метадані файлу — відкритий текст), без relay/TURN.

## Ключове архітектурне обмеження

Ніколи не розробляти й не хостити власну інфраструктуру (relay/TURN, сервер сигналізації) — принципова межа проєкту, не поточна нестача. Мережева інформація йде лише через канал хендшейку (месенджер). Дозволено: власний роутер (UPnP/NAT-PMP/PCP, ручний проброс порту) і готовий безкоштовний публічний STUN (лише дізнатись адресу, нічого не хоститься). Фолбек з'єднання: UPnP → STUN → fail (LAN-only, попередження про неможливість P2P). Деталі — [concept.md](concept.md) → «Принципове архітектурне обмеження».
