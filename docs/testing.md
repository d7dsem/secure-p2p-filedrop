# Концепція тестування (старт — на одному ПК)

Мета: перевіряти без двох фізичних машин — навіть реальний P2P-транспорт (Фаза 3, [concept.md](concept.md)) через loopback (Рівень 3). Шари тестів = шари коду. Модулі, тестові групи, які групи запускати після якої зміни — [architecture.md](architecture.md); тут лише рівні тестування й ручні чеклісти.

## Рівень 1 — модульні тести чистої логіки (без GUI, без мережі)

`connection.py`/`exchange.py` не залежать від tkinter — тестуються напряму. `unittest` (стдліб); `test_exchange.py` додатково потребує `pyzipper` (`requirements.txt`).

```
tests/
  test_connection.py
  test_exchange.py
```

Що перевіряється — див. самі тести. Модуль → тестова група — [architecture.md](architecture.md). Рівень запускається за секунди, без вікон — тут ловити регресії деривації ключа/парсингу хендшейку.

### `appearance.py` — не лише Рівень 2

Клік по пікселю/колонці дерева лишається ручним (Рівень 2), але логіка стану `SecureFileClientApp` тестується напряму на прихованому (`root.withdraw()`) `tk.Tk()`: [`tests/test_appearance.py`](../tests/test_appearance.py), група `gui`. Пропускається (`skipTest`) без tkinter/дисплея.

## Рівень 2 — Фаза 1 (хендшейк) вручну на одному ПК, два вікна GUI

Логіка стану вже покрита автоматично (вище); ручний чекліст лише для реального віджета/мережі:

1. Запустити застосунок двічі (`python src/secure_file_drop_entry.py`).
2. **Позитивний**: однакова passphrase в A і B → хендшейк A → вставити в B → коди підтвердження **збігаються**.
3. **Негативний**: різна passphrase → коди **не збігаються**, в обох вікнах віконце "Ключі не збігаються". Однакова виправлена фраза + OK в обох → "Підтверджено" без повторного пересилання хендшейку (текст у A не змінився). Cancel в A — A слухає далі; Cancel у B — статус "Ключі НЕ збігаються — ... вставте хендшейк ще раз".
4. **Пошкоджений хендшейк**: обрізати символи в B → керована помилка (`ValueError`), не крах.

Прогонити після зміни `connection.py`/`appearance.py`, що торкається полів хендшейку.

5. **"Налаштувати з'єднання (UPnP → STUN)"** — потребує реальної мережі (`test_nat_traversal.py`/`test_stun_client.py` тестують лише парсинг):
   - UPnP увімкнено → `net=` показує "публічна, через UPnP (порт прокинуто)";
   - UPnP вимкнено, є інтернет → падає керовано (`UpnpUnavailable`), STUN відпрацьовує: "публічна, через STUN (порт НЕ прокинуто)";
   - обидва недоступні → керований фолбек на локальну LAN-адресу, попередження про неможливість P2P без relay; застосунок не падає в жодному випадку.
6. **Дерево каталогу + пакування** (клік/розгортання — ручне, логіка навколо покрита `test_exchange.py`):
   - каталог з підкаталогами → розмір кожного елемента, лінива підвантаження;
   - зняти позначку з файлу/підкаталогу (каскадно) → "Запакувати обране" створює ZIP лише з позначеного в `<каталог>/.secure_p2p_filedrop_pack/payload.zip`;
   - повторне відкриття того ж каталогу → технічна підпапка не з'являється в дереві;
   - зняти всі позначки → попередження, не порожній архів.

## Живий STUN-запит — окрема ручна перевірка

LAN не може зловити баги трансляції портів (порти завжди збігаються без NAT). Реальний тест проти публічного STUN спіймав такий баг раніше (зовнішній порт відрізнявся від локально введеного).

Не частина `unittest discover` (мережева залежність, флейково) — окрема перевірка перед релізом чи після зміни `stun_client.py`/`nat_traversal.py`:

```python
from stun_client import get_public_address
ip, port = get_public_address(local_port=52075)
print(ip, port)  # звір port з тим, що пішло в хендшейк
```

Розбіжність порту, що не потрапляє в хендшейк, — регресія.

## Рівень 3 — сервісна функція + Фаза 3 — на одному ПК

`src/transport.py` тестується через loopback (`127.0.0.1`, різні порти) замість двох ПК — без GUI, без `subprocess`: [`tests/test_transport.py`](../tests/test_transport.py), група `transport`.

Окремо перевірено вручну (не в автотесті): повний GUI E2E — два `SecureFileClientApp` на прихованих `tk.Tk()`, хендшейк, канал, передача файлу в обидва напрямки — байт-у-байт збіг.

**Відома нестабільність (не продакшн-баг)**: `EstablishConnectionTests`/`VerifyChannelTests`/`SendReceiveFilesTests` іноді флейкають (`KeyError`/`WinError 10053`) — тест навмисно змушує ОБИДВІ сторони одночасно приймати й підключатись, можливі дві незалежні TCP-сесії. У реальному застосунку так не буває (рівно одна сторона завжди "лише слухає") — артефакт тестового сетапу, повторний запуск проходить.

Не автоматизовано: **великий файл** (сотні МБ – кілька ГБ) — ручний Рівень 2, генерувати `os.urandom`-скриптом, не зберігати в репозиторії. Перше підняття серверного сокета на Windows може триггерити запит Firewall — очікувано.
