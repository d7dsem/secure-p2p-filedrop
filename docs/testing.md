# Концепція тестування (старт — на одному ПК)

Мета: перевіряти застосунок без потреби у двох фізичних машинах — принаймні поки не з'явиться реальний мережевий P2P-транспорт (Фаза 3 у [concept.md](concept.md)). Тести розбиті по тих самих шарах, що й код (`connection.py` / `exchange.py` / сервісна функція / `appearance.py`), щоб не змішувати логіку з GUI так само, як не змішуємо перевірку з'єднання з передачею файлу.

## Рівень 1 — модульні тести чистої логіки (без GUI, без мережі)

Найдешевший і найшвидший рівень. `connection.py` та `exchange.py` вже не залежать від tkinter — їх можна тестувати напряму функціями, без відкриття вікон. `unittest` зі стандартної бібліотеки; `test_exchange.py` додатково імпортує `pyzipper` (єдина зовнішня залежність проєкту — `requirements.txt`), тому перед прогоном тестів має бути встановлена.

Структура:
```
tests/
  test_connection.py
  test_exchange.py
```

### `test_connection.py` — що перевіряти

- **`derive_key`**
  - однакові `(passphrase, salt, iterations)` → завжди однаковий ключ (детермінованість)
  - зміна хоч одного символу в passphrase → інший ключ (лавинний ефект — непряма перевірка, що дерivація не "ламається" мовчки)
  - різна `salt` при однаковому passphrase → інший ключ
  - довжина результату — 32 байти (SHA-256)
- **`key_fingerprint`**
  - довжина рядка == `CONNECTION.fingerprint_hex_length` (8)
  - результат — верхній регістр, лише hex-символи
  - однаковий ключ → однаковий фінгерпринт; інший ключ → інший фінгерпринт (з високою ймовірністю — тест на конкретних відомих байтах, не "на удачу")
- **`build_handshake_packet` + `parse_handshake_packet` (round-trip)**
  - побудувати пакет → розпарсити → `salt`/`iterations`/`session_id`/`host`/`port` збігаються з тим, що було на вході побудови (`host`/`port` — мережевий компонент хендшейку, додано разом з CLI-параметром `--pswd`)
  - пошкоджений/обрізаний текст → `ValueError`
  - порожній рядок → `ValueError`
  - відсутнє обов'язкове поле (`v`/`sid`/`salt`/`iter`/`host`/`port`) → `ValueError`
- **CLI (`secure_file_drop_entry.parse_args`)** — не залежить від GUI, тестується напряму: `--pswd`/`-p` заповнюють passphrase, без прапорця — `None`.

### `test_exchange.py` — що перевіряти

- **`prepare_archive`**
  - для файлу (`is_dir=False`) — повертає той самий шлях без змін
  - для каталогу (`is_dir=True`) — повертає шлях до ZIP, файл справді існує
  - вміст ZIP відповідає вмісту вихідного каталогу (порівняти список імен файлів усередині архіву з `os.walk` по оригіналу)
  - порожній `path` → `ValueError`
- **`format_size`** — межі одиниць (Б/КБ/МБ/ГБ), нуль байтів
- **`list_entries`** — лише один рівень (без вкладених), каталоги перед файлами за іменем, агрегований розмір каталогу = сума файлів усередині, `exclude_names` пропускається на будь-якому рівні обходу (не лише в корені)
- **`build_archive_from_selection`** — архів у технічній підпапці кореня (не system temp), містить лише передані `included_files`, порожній список → `ValueError`, підпапка після пакування сама не з'являється в наступному `list_entries`
  - **шифрування/стиснення**: `EncryptionLevel.NONE` → архів читається звичайним stdlib `zipfile`; `compress=True/False` → `ZIP_DEFLATED`/`ZIP_STORED`; AES128/256 з правильним паролем розшифровується (round-trip через `pyzipper`), з неправильним — падає, без пароля при AES → `ValueError`

Цей рівень запускається за секунди, без відкриття жодного вікна — тому саме тут варто ловити регресії деривації ключа чи парсингу хендшейку, а не вручну клікаючи по GUI щоразу.

### Уточнення: `appearance.py` — не завжди "тільки Рівень 2"

Спочатку думали, що весь `appearance.py` — суто ручний Рівень 2, бо tkinter важко автоматизувати. Виявилось не зовсім так: **клік по пікселю чи по колонці дерева** дійсно вимагає реального віджета й лишається ручним, але **логіка стану класу** `SecureFileClientApp` (що відбувається з `selected_path`/`packed_archive_path`/`_file_tree_checked` після виклику обробника) — це звичайний Python-код, який можна викликати напряму на прихованому (`root.withdraw()`) `tk.Tk()`-екземплярі без жодної участі людини. Саме так спіймано реальний баг: `on_pack_selected` перезаписував `selected_path`/`selected_is_dir` шляхом архіву, тому другий клік "Запакувати обране" (після зняття позначки з файлу) одразу падав на guard-перевірці "Спочатку оберіть каталог" — виправлено (тепер шлях архіву зберігається окремо в `packed_archive_path`, `selected_path` лишається каталогом), регресія закрита в [`tests/test_appearance.py`](../tests/test_appearance.py). Тест пропускається (`skipTest`), а не падає, якщо tkinter/дисплей недоступні (headless Linux CI без Xvfb).

## Рівень 2 — Фаза 1 (хендшейк) вручну на одному ПК, два вікна GUI

Поки автоматичних GUI-тестів немає (tkinter важко автоматизувати headless), це ручний чекліст — по суті формалізація того, що вже обговорювали:

1. Запустити застосунок двічі (`python src/secure_file_drop_entry.py` у двох терміналах) — два незалежні процеси, без конфлікту.
2. **Позитивний сценарій**: однакова passphrase в обох вікнах → згенерувати хендшейк у A → вставити в B → коди підтвердження в обох вікнах **збігаються**.
3. **Негативний сценарій**: різна passphrase в A і B → коди підтвердження **не збігаються** — підтверджує, що механізм справді ловить розбіжність, а не завжди показує "успіх".
4. **Пошкоджений хендшейк**: обрізати кілька символів з вставленого тексту в B → очікується керована помилка розбору (`ValueError` з `parse_handshake_packet`, показана користувачу), а не крах застосунку.

Цей рівень варто прогонити вручну після будь-якої зміни в `connection.py` чи `appearance.py`, що торкається полів хендшейку.

5. **Кнопка "Налаштувати з'єднання (UPnP → STUN)"** — триетапна модель з docs/concept.md, потребує реальної мережі, автотестом не покривається (`tests/test_nat_traversal.py` і `tests/test_stun_client.py` тестують лише парсинг/кодування, без живого роутера чи STUN-сервера):
   - **роутер з увімкненим UPnP**: очікується успіх на рівні 1, у логу — зовнішня IP, `net=` у хендшейку показує `публічна, через UPnP (порт прокинуто)`;
   - **UPnP вимкнено, є доступ в інтернет**: рівень 1 падає керовано (`UpnpUnavailable` у лозі), рівень 2 (STUN) відпрацьовує — `net=` показує `публічна, через STUN (порт НЕ прокинуто)`;
   - **немає інтернету/UPnP і STUN обидва недоступні** (напр. ізольована LAN): обидва рівні падають керовано, з'являється попередження (messagebox) про неможливість P2P без relay, хендшейк все одно генерується з локальною LAN-адресою — застосунок не падає в жодному з трьох випадків.
6. **Дерево вмісту каталогу + пакування обраного** ("Обрати каталог..." у вкладці "Сеанс") — клік по чекбоксу й розгортання каталогу залежать від реального віджета tkinter, автотестом не покриваються (логіка навколо — `list_entries`/`build_archive_from_selection` — покрита в `tests/test_exchange.py`):
   - обрати каталог з підкаталогами → дерево показує розмір кожного елемента, підкаталог розгортається лінивo (стрілка з'являється одразу, вміст довантажується лише при кліку);
   - зняти позначку з файлу і з цілого підкаталогу (каскадно знімає позначки з усіх його нащадків, включно з ще не розгорнутими) → "Запакувати обране" створює ZIP лише з решти позначених файлів у `<обраний каталог>/.secure_p2p_filedrop_pack/payload.zip`;
   - повторно відкрити "Обрати каталог..." на тому самому каталозі після пакування → технічна підпапка `.secure_p2p_filedrop_pack` НЕ з'являється в дереві;
   - зняти позначки з усього → "Запакувати обране" показує попередження (messagebox), а не порожній архів.

## Живий (реальний, не мокнутий) STUN-запит — окрема ручна перевірка

**Знайдений прецедент**: на LAN усі порти завжди збігаються (немає NAT-трансляції), тому локальне тестування *в принципі не може* зловити баги трансляції адрес/портів. Реальний тест проти живого публічного STUN (`stun_client.get_public_address`) одразу спіймав такий баг — зовнішній порт, який реально бачить NAT, відрізнявся від локально введеного, а `appearance.py` до фіксу клав у хендшейк локальний, а не реальний порт.

Це **не** частина автоматичного `unittest discover` (мережевий виклик до чужого сервера — повільно, флейково, залежить від інтернету й типу NAT користувача), а окрема ручна перевірка перед релізом чи після будь-якої зміни в `stun_client.py`/`nat_traversal.py`/логіці, що споживає їхній результат:

```python
from stun_client import get_public_address
ip, port = get_public_address(local_port=52075)
print(ip, port)  # звір port із тим, що реально пішло в згенерований хендшейк
```

Якщо зовнішній `port` тут відрізняється від локального — і різниця не потрапляє в сам хендшейк — це регресія того самого бага.

## Рівень 3 — сервісна функція + Фаза 3 (коли будуть реалізовані), теж на одному ПК

Реальний мережевий P2P-транспорт можна тестувати без другого фізичного ПК — обидва "клієнти" підключаються через **loopback** (`127.0.0.1`) на різні порти замість реальної IP-адреси іншої сторони. Стандартна практика для локального тестування сокетів.

Пропозиція для реалізації, щоб це залишалось тестовним і без tkinter:
- Логіку сервісної функції (встановлення й перевірка з'єднання) і Фази 3 (передача) варто, за прикладом `connection.py`/`exchange.py`, винести в окремий модуль **без залежності від GUI** (наприклад `transport.py`) — тоді інтеграційний тест зможе імпортувати й викликати його напряму з `tests/`, без запуску вікон і без `subprocess`.
- Тест-сценарій: підняти "сервер" на `127.0.0.1:PORT_A`, "клієнта" на `127.0.0.1:PORT_B` в тому самому тестовому процесі (або в двох потоках/процесах), прогнати хендшейк із Рівня 1, дочекатись підтвердження сервісної функції, передати тестовий файл, звірити **SHA-256 контрольну суму** відправленого й отриманого файлу.
- Окремо варто протестувати **великий файл** (сотні МБ – кілька ГБ, це цільовий розмір з concept.md) хоча б один раз навіть без реальної мережі — щоб зловити проблеми з пам'яттю/продуктивністю на етапі архівування (`prepare_archive`) раніше, ніж на етапі транспорту. Genерувати такий файл можна тестовим скриптом (наприклад, `os.urandom`-заповнений файл потрібного розміру в тимчасовій директорії), не зберігати його в репозиторії.
- На Windows перше підняття серверного сокета (навіть на loopback) іноді триггерить запит Windows Firewall — це очікувано під час першого ручного прогону, не помилка коду.
