# Нотатки реалізації

Технічні рішення й причини, які не влазять у коментар коду. Кожен розділ = одне місце в коді.

## tests/

### tests/_pathfix.py + tests/__init__.py
`src/` не пакет (модулі імпортують напряму, напр. `from tuning import CONNECTION`). Кожен тестовий модуль робить `import _pathfix` першим рядком, щоб додати `src/` у `sys.path` до будь-якого імпорту — працює за будь-якого способу запуску тестів, на відміну від `tests/__init__.py` (не встигає відпрацювати першим при `unittest discover -s tests` без `-t`).

### tests/test_appearance.py
Тестує логіку стану `SecureFileClientApp` (не кліки/пікселі — це Рівень 2, `docs/testing.md`) напряму на прихованому (`withdraw()`) tkinter-віджеті. Пропускається (`skipTest`), якщо tkinter/дисплей недоступні. `HOME`/`USERPROFILE` підмінені тимчасовою директорією.

### tests/test_nat_traversal.py
Без реальної SSDP-розсилки/SOAP до живого роутера (це ручний тест). Перевіряється лише мережево-незалежне: парсинг XML, SOAP-тіло, заголовки SSDP.

### tests/test_stun_client.py
Без реального UDP-обміну з публічним STUN. Перевіряється лише кодування Binding Request і розбір синтетичного Binding Response.

### tests/test_local_config.py
Явний `path` замість `~/config.json` — тести не чіпають реальний домашній каталог.

## secure_file_drop_entry.py

Точка входу. Карта шарів/модулів — [architecture.md](architecture.md); деталі кожного модуля — розділи нижче й `docs/concept.md`.

Залежності: стандартна бібліотека + `pyzipper` і `pycryptodomex` (`requirements.txt`; `pycryptodomex` — транзитивна залежність `pyzipper`, нового встановлення не додає).

## connection.py

### on_generate_passphrase — token_urlsafe, не diceware-словник
`secrets.token_urlsafe(24)` (~192 біти) замість diceware-словника — фраза й так копіюється через той самий канал (месенджер), що й хендшейк, голосове відтворення не типове. Простіше, без нової залежності.

### derive_key — чому PBKDF2-HMAC
Раніше — ручний `SHA-256(SHA-256(...))` без HMAC (слабший компроміс на старті проєкту). Замінено на `hashlib.pbkdf2_hmac` (стдліб).

### ConnectionTuning.default_iterations / min_iterations
Піднято 200_000 → 600_000 (OWASP для PBKDF2-HMAC-SHA256, знайдено security-ревʼю). `appearance.py::on_process_incoming` окремо затискає `iterations` знизу через `min_iterations` — захист від підробленого/заниженого `iter` у ЧУЖОМУ пакеті (`parse_handshake_packet` значення не валідує, лише наявність поля). Сам парсер лишається чистим без клемпінгу — інакше зламався б round-trip тест на малі `iter` (`test_connection.py`).

### key_fingerprint — навіщо він взагалі
Короткий код для звірки голосом/текстом через месенджер, без передачі самого ключа.

### detect_local_address
Best-effort локальна IP хоста (docs/concept.md, Фаза 1, п.1) — адреса локального інтерфейсу, НЕ публічна. Інтернет/NAT — це вже `nat_traversal.py`/`stun_client.py`.

### build_handshake_packet — параметр host
`host=None` — автовизначення локальної адреси. Якщо викликач уже має публічну IP (UPnP/STUN) — передає напряму, вона йде в пакет.

## exchange.py

### prepare_archive — чому досі без пароля/AES
Старий шлях (перша версія), стдлібний `zipfile` без AES — новий шлях (`build_archive_from_selection`, `pyzipper`) покриває цей випадок. GUI-флоу не використовує (лише старі тести).

### build_archive_from_selection — pyzipper, AES-пароль = сесійний ключ
`pyzipper` — єдина зовнішня залежність (докладніше — `docs/concept.md`, "Відомі технічні компроміси"). AES-пароль — уже деривований сесійний ключ (`local_key`), окремого обміну секретом не потрібно.

## nat_traversal.py

### Модуль — межі відповідальності
Говорить лише з роутером у LAN користувача (SSDP + SOAP на control URL із XML-опису роутера) — жодного зовнішнього сервера. Роутер без UPnP (вимкнено/CGNAT) → `UpnpUnavailable`/`UpnpActionError`, `appearance.py` падає на рівень 2 (STUN) чи ручний ввід IP/проброс порту. Модель у цілому — `docs/concept.md`, "Принципове архітектурне обмеження".

## stun_client.py

### Модуль — чим відрізняється від nat_traversal.py
Разовий stateless UDP Binding Request до публічного STUN — сервер лише відлунює адресу, файлових даних чи ключа туди не йде, застосунок нічого не хостить. На відміну від UPnP (говоримо з ВЛАСНИМ роутером, просимо прокинути порт) — тут лише дізнаємось адресу; порт лишається непрокинутим (NAT-мапінг тримається лише поки триває UDP-обмін).

## local_config.py

### Модуль — чим відрізняється від tuning.py
`tuning.py` — жорсткі дефолти в коді. `local_config.py` — значення, які користувач редагує в рантаймі й свідомо зберігає кнопкою "Зберегти профіль"; доти зміни лише в пам'яті сеансу.

### load_config
Немає файлу/пошкоджений → дефолти, одразу зберігаються на диск, щоб `client_id` закріпився з першого запуску, а не генерувався щоразу.

### LocalConfig.default_port — precedence і сумісність зі старими профілями
Дефолт порту тепер живе в профілі, не лише в `tuning.CONNECTION.default_port`. Повна ієрархія (низ → верх): `CONNECTION.default_port` (лише коли в профілі його взагалі нема) < `profile.default_port` < CLI `--port` < ручна правка поля "Порт" у GUI (сеансова, у профіль не пишеться) — реалізація в `appearance.py` (`var_port` init + `on_save_profile`). `_parse_port` валідує значення з файлу (ціле 1..65535); відсутнє поле (профіль, збережений до цієї зміни), биту-типу чи поза межами значення — тихий fallback на `CONNECTION.default_port`, без падіння застосунку. Зворотна сумісність: старий файл профілю без `default_port` читається нормально (`_parse_port(None, ...)` → fallback), при першому збереженні поле дописується.

## tuning.py

### ProfileTuning
Лише ДЕ шукати конфіг і які дефолти підставити при першому запуску — не поточні значення (вони в `local_config.py`/файлі).

### AppearanceTuning.window_geometry
900×680 (двоколонковий layout) — старий 640×720 не вміщав дерево файлів. Знайдено реальними скріншотами під час UX-огляду.

### AppearanceTuning — палітра темної теми
Ttk не має темної теми "з коробки" — кольори задаються вручну через `ttk.Style` (ttk-віджети) і `.configure()` (класичні Tk-віджети: `Text`/`ScrolledText` стилем не керуються).

### AppearanceTuning.accent_button_bg
`dark_accent` зі світлим текстом (`#e6e6e6`) — контраст ~3.1:1, нижче WCAG AA (4.5:1). `accent_button_bg` (темніший) з білим текстом — ~6.3:1. Виміряно при UX-огляді.

### ExchangeTuning.pack_subdir_name
Технічна підпапка в корені каталогу передачі для архіву обраного (`appearance.py`, дерево з чекбоксами). Виключена зі сканування, щоб не запакувати сама себе.

## appearance.py

### _apply_dark_theme — іменовані шрифти
Базовий шрифт трохи збільшений (дефолт Tk дрібний). Окремі шрифти для заголовків секцій і моноширинного тексту хендшейку. Посилання тримаються як атрибути `self` — інакше Python їх прибирає, шрифт злітає до дефолту.

### _make_checkbutton
`ttk.Checkbutton` теми "clam" малює позначений стан хрестиком (читається як "ні", контрінтуїтивно). Plain `tk.Checkbutton` на Windows малює галочку — кольори під темну тему задані вручну (tk-віджети не підпорядковані `ttk.Style`).

### Treeview.Heading — hover-фікс
Без окремого `style.map` для "active"/"pressed" тема "clam" при наведенні/кліку на заголовок колонки падає на світлий дефолт.

### _make_scrollable
Ліва колонка вкладки "Сеанс" не вміщається по висоті на дефолтному розмірі вікна (дерево файлів взагалі не влазило — головна знахідка UX-огляду). `Canvas` + `Scrollbar` + `Frame` через `create_window` — стандартний tkinter-патерн (ttk своєї прокручуваної рамки не має).

### _build_session_tab — двоколонковий layout
Замінив однорядне стекування секцій: зліва — ідентичність/з'єднання (прокручується), справа — дерево файлів на всю висоту.

### frame_conn — фіксована висота під статус
Текст статусу росте з 1 рядка до 2 (фінальний результат UPnP/STUN) — без фіксованої висоти ліва колонка "стрибала". Виміряно: 23px/1 рядок, 40px/2 — контейнер завжди на 2-рядковій висоті.

### _make_reserved_label
Хелпер того самого фікса: `ttk.Frame` фіксованої висоти (`pack_propagate(False)`) навколо `ttk.Label`. Скрізь, де текст лейбла міняється в рантаймі: статус мережі, підтвердження ключа, обраний файл/каталог, статус каналу. Висота підібрана під найдовший реальний текст.

### _start_connection_setup — фонова автоперевірка
Триетапна модель UPnP → STUN → LAN-only (`docs/concept.md`), запускається автоматично — сервісна функція. Мережеві виклики (до кількох секунд) — у фоновому потоці, щоб не заморожувати GUI; результат — через `queue.Queue`, забирається `root.after()`-опитуванням (`_poll_connection_setup`) — прямі виклики tkinter із чужого потоку небезпечні.

### on_generate_handshake — public_port
Спостережений зовнішній порт: UPnP — той самий, що локальний; STUN — NAT міг підмінити (перевірено: локальний 52075 мапнувся на інший). Якщо з'єднання не налаштовувалось — `public_port=None`, у пакет іде локально введений порт.

### on_initiate_transfer / _set_checked_recursive — незмінність selected_path
`selected_path`/`selected_is_dir` не змінюються після ініціалізації передачі — інакше повторна ініціалізація падає на guard-перевірці. Виправлений баг: раніше сюди писався шлях архіву, другий клік бачив `selected_is_dir=False` і відмовляв, хоча дерево лишалось на екрані.

### packed_archive_path — навіщо окремо від selected_path
Тримає шлях зібраного архіву окремо, щоб `selected_path` лишався незмінним. `_transfer_root_dir()` читає `packed_archive_path`, якщо є, інакше `selected_path`/`selected_is_dir`.

### _session_key — local_key проти peer_key
Хендшейк ділиться лише в ОДИН бік. Сторона, що ЗГЕНЕРУВАЛА, тримає ключ у `local_key`; сторона, що ЛИШЕ ОБРОБИЛА чужий хендшейк, кладе деривований ключ у `peer_key` (`local_key` лишається `None`). `_session_key()` повертає `peer_key`, якщо є, інакше `local_key` — для AES-пароля архіву, HMAC-підтвердження, шифрування передачі. Знайдено через E2E-тест з помилковим сценарієм (обидва боки викликали `on_generate_handshake()`).

### channel_key — окремо від local_key/peer_key
Копія значення, яким РЕАЛЬНО verified канал (`_session_key()` у момент `_maybe_start_channel_establishment`), збережена окремо — щоб `_receive_worker`/`on_send_files` не переобирали "local чи peer" і не розійшлись зі значенням підтвердження, якщо один з атрибутів пізніше зміниться.

## transport.py

### Межі відповідальності
Шар "транспорт": сервісна функція (з'єднання) + Фаза 3 (передача) з `docs/concept.md`. Без GUI-залежностей — `appearance.py` викликає у фонових потоках, результат — через `queue.Queue` (`_channel_queue`).

### establish_connection — чому peer_host/peer_port опційні ("режим слухати")
Сторона, що ЗГЕНЕРУВАЛА хендшейк, ще не знає адреси іншої — слухає на своєму порту (`_accept_worker`); інша, знаючи host/port з хендшейку, підключається сама (`_connect_worker`). Функція запускає обидва одночасно; хто перший встановив з'єднання — переміг, другий скасовується спільним `done`-Event. Hole-punching не потрібен: досить, щоб ХОЧ ОДИН бік був досяжний ззовні (адресу підготували UPnP/STUN).

### establish_connection — скидання таймауту сокета після виграшу
`listener.accept()`/`sock.connect()` мають короткий таймаут (щоб цикл перевіряв `stop_event`/дедлайн), який лишався й ПІСЛЯ з'єднання, якщо не скинути явно. Знайдений баг: фаза передачі отримувала спорадичні `TimeoutError` на повільних передачах. Фікс: `sock.settimeout(None)` одразу після `accept()`/`connect()`.

### establish_connection — bind_error, чому не просто чекати timeout
Знайдено code-ревʼю: `listener.bind()`-помилка (порт зайнятий) тихо вбивала `_accept_worker`, виклик чекав повний `connect_timeout_seconds` (300с) і показував загальне "не вдалось з'єднатись". Тепер помилка кладеться в `result["bind_error"]` і в режимі "лише слухати" фатальна одразу — конкретне повідомлення про зайнятий порт замість generic timeout.

### establish_connection — SO_EXCLUSIVEADDRUSE на Windows, не SO_REUSEADDR
Знахідка code-ревʼю: `SO_REUSEADDR` на Windows дозволяє ДРУГОМУ сокету прив'язатись до порту, який вже слухає — невизначено, хто реально прийме з'єднання (два інстанси застосунку на одному ПК на тому самому порту). Фікс: якщо є `socket.SO_EXCLUSIVEADDRUSE` (Windows) — використовуємо його, конфлікт ловиться на `bind()` з чіткою помилкою; POSIX лишає `SO_REUSEADDR`.

### establish_connection — self-connect (_is_self_connect)
Рідкісний TCP edge-case: `peer_host:peer_port` збігається з власним listener'ом цього ж процесу — стек з'єднує сокет сам із собою. `_connect_worker` перевіряє `getsockname() == getpeername()` одразу після `connect()`; винесено в окремий `_is_self_connect` для юніт-тесту (реальний self-connect недетермінований — залежить від ОС/видачі ефемерного порту).

### establish_connection — stop_event гонка після виграшу
Якщо `stop_event` встановили ЗОВНІ (напр. скидання сесії в `appearance.py`) саме в момент, коли воркер уже виграв гонку, функція не повертає мовчки "виграний" сокет — закриває його й кидає `ConnectionFailed`. Знімок `stop_event.is_set()` береться ДО власного `stop_event.set()` (яким функція сигналізує програвшому воркеру), інакше не відрізнити зовнішнє скасування від свого ж cleanup-сигналу.

### connect_timeout_seconds — чому 300, не 15
15с виходило з припущення миттєвого з'єднання — реальний флоу: A генерує й одразу слухає, B ще копіює пакет, відкриває месенджер, вставляє, обробляє — хвилини, не секунди. Тести передають короткий timeout явно, дефолт нічого не ламає.

### verify_channel — HMAC challenge-response, ключ ніколи не йде по мережі
Симетрично: обидві сторони шлють випадковий nonce, у відповідь `HMAC(key, чужий_nonce)`, звіряють через `hmac.compare_digest` (захист від timing-атак). Різні ключі (одруківка в фразі, пошкоджений хендшейк) → провал тут, а не мовчазний побитий файл пізніше.

### verify_channel — мережеві збої ≠ VerificationError
Знахідка code-ревʼю (HIGH): раніше БУДЬ-яка помилка (таймаут, обрив, OSError) під час підтвердження ключа перетворювалась на `VerificationError` → UI показував "ключі не збігаються" й пропонував ввести пароль ще раз, хоча причина — мережа. Тепер `VerificationError` кидається ЛИШЕ коли код підтвердження реально отримано й не збігся; таймаут/`PeerClosed`/`OSError`/завеликий кадр → `ConnectionFailed` (як і `establish_connection`). ПРИМІТКА: `appearance.py._channel_establish_worker` після виклику `verify_channel` наразі ловить лише `VerificationError` окремо, а решту (включно з новим `ConnectionFailed`) — спільним `except Exception` як `verification_failed`; щоб класифікація подій дійшла до UI коректно, там потрібен додатковий `except ConnectionFailed` ПЕРЕД цим `except Exception`, що кладе подію `connection_failed` — навмисно не зроблено тут (поза дозволеним для цієї задачі файлом).

### send_files/receive_files — AES-256-CTR, окремий nonce на файл
Ключ — уже підтверджений сесійний ключ. Свіжий nonce на КОЖЕН файл — щоб keystream не повторювався між файлами в межах одного сеансу з кількома передачами. SHA-256 оригінального вмісту перевіряється після прийому; розбіжність → файл видаляється одразу (`os.remove`).

### receive_files — захист від path traversal
`rel_path` у заголовку контролюється іншою стороною (потенційно ворожою) — перевіряється, що `dest_path` не виходить за межі `dest_dir` (`../../etc/passwd`-стиль), перш ніж писати на диск. Перевірено тестом з таким заголовком напряму.

### _invalidate_session_if_active — знайдений реальний баг
Два інстанси на одному ПК: поле "Порт" показувало інше значення, ніж те, на якому реально слухав канал — порт змінили ПІСЛЯ генерації хендшейку, коли `_maybe_start_channel_establishment` уже зафіксував старе значення. Фікс: `trace_add("write", ...)` на `var_passphrase`/`var_iterations`/`var_port` викликає `_invalidate_session_if_active` — якщо сеанс активний, скидає local_key/peer_key/канал, повідомляє про потребу нового хендшейку.

### _session_epoch — чому недостатньо просто скинути стан
Фонові потоки (`establish_connection`/`verify_channel`/`receive_files`/`send_files`) не переривні. Просте скидання `channel_socket` не завадить старому потоку дописати подію в чергу поверх уже нового стану — стара сесія "воскресне". Кожен івент тегується `self._session_epoch` на момент старту потоку; `_invalidate_session_if_active` інкрементує epoch; `_handle_channel_event` ігнорує подію з чужим epoch.

### _make_readonly_selectable / keycode — keycode, не keysym
Ctrl+V/C/A не спрацьовували під нелатинською розкладкою на Windows: стандартні Tk-біндинги (`<Control-Key-v>`) прив'язані до **keysym** (символ за ПОТОЧНОЮ розкладкою); під ЙЦУКЕН фізична "V" дає інший keysym. `event.keycode` — номер фізичної клавіші (Windows virtual-key code: A=65, C=67, V=86), від розкладки не залежить.

Фікс: `_block_edit` викликає `event_generate("<<Copy>>")`/`tag_add("sel",...)` за keycode; Ctrl+V (keycode=86) у полі хендшейку — через `on_paste`. Тест потребує реального фокуса (`root.deiconify()`) — синтетичні події на withdrawn-вікні не долітають.

### _maybe_start_channel_establishment — hairpin NAT попередження + тікер очікування
Два інстанси на одному ПК отримали через STUN однакову публічну адресу — конектор намагався достукатись до неї зсередини тієї ж мережі (потрібен NAT hairpin, не всі роутери вміють), статус висів без пояснення до 300с. Дві дії:

1. `_is_private_host(host)` — якщо адреса іншої сторони не приватна, одразу в лог і в підсумкове повідомлення додається попередження про hairpin NAT.
2. `_tick_channel_wait` — раз/секунду дописує `(Nс)` до статусу, поки `_channel_pending` не стане `False`. Керується тим самим `_session_epoch` — старий тікер сам зупиняється.

### send_ping / receive_files(on_control=...) / on_test_channel
Спосіб перевірити канал живий без справжніх файлів. Ping/pong control-кадр ПОВЕРХ протоколу кадрів (не окремий `recv()` — сокет уже має одного постійного читача, `_receive_worker`; другий змагався б за той самий потік). `send_ping` пише `{"type":"ping"}`; `receive_files` розпізнає вхідний `"ping"`, відповідає `"pong"` (`continue`, не `return`), яке підхоплюється тим самим циклом через `on_control`. `on_test_channel` відповіді сам не читає — pong приходить асинхронно.

### on_paste_handshake — clipboard_get напряму
Вставка через Ctrl+V іноді не спрацьовувала (Tk `Text` не має контекстного меню, фокус/ОС/термінал можуть перехоплювати комбінації). Кнопка "Вставити хендшейк" читає `root.clipboard_get()` напряму — не залежить від цих механізмів.

### --port CLI-параметр
Той самий патерн, що `--pswd`/`--snd-dir`: заповнює `var_port` при старті. Мотивація — знайдений баг, коли зміна порту вручну ПІСЛЯ генерації хендшейку плутала стан (тепер виправлено інвалідацією, але простіше не чіпати поле після старту): два інстанси запускаються одразу з різними портами через `.vscode/launch.json`.

### var_port — дефолт з профілю, precedence з CLI/ручною правкою
`var_port` тепер ініціалізується `self.profile.default_port` (не `CONNECTION.default_port` напряму — профіль сам fallback-иться на нього при завантаженні, `local_config.py`), CLI `--port` підставляється поверх ПІСЛЯ `_build_ui` як і раніше. Два допоміжні прапорці відстежують решту ієрархії: `_cli_port_provided` (чи задано `--port` цього запуску) і `_port_overridden_by_user` (чи користувач сам відредагував поле "Порт" цього сеансу — окремий `trace` `_mark_port_overridden`, не плутати з `_invalidate_session_if_active`, який реагує на ті самі записи, але скидає сеанс). `_suppress_port_override_tracking` — той самий патерн, що `_suppress_param_invalidation`, лише вужчий: гасить саме позначку "ручна правка" на programmatic `set()` (initial/CLI/синхронізація з вкладки "Профіль"), не саму інвалідацію сеансу — програмна зміна порту з вкладки "Профіль" СПРАВДІ повинна інвалідувати активний сеанс (стара адреса), просто не повинна виглядати як "користувач сам відредагував".

`on_save_profile`: зміна дефолтного порту профілю синхронізує `var_port` (той самий `set()`, під тим самим suppression) лише коли `not _port_overridden_by_user and not _cli_port_provided` — свідомо просте правило (не намагається відстежувати "яке джерело зараз активне" складніше): якщо користувач уже сам вибрав порт цього сеансу, чи явно задав `--port`, профіль його не чіпає, оскільки обидва стоять вище в ієрархії.

### on_open_incoming_dir — навіщо саме profile.incoming_dir, не var_incoming_dir
Відкриває `self.profile.incoming_dir` (те, що РЕАЛЬНО передається в `receive_files`) — не незбережене поле вводу. Кросплатформенно: `os.startfile`/`open`/`xdg-open`.

### _send_worker / _receive_worker — прогрес-бар, агреговано vs по файлу
Send знає повний список файлів і розміри заздалегідь — рахує агрегований прогрес по пакету. Receive дізнається про файл лише з його заголовка, про завершення — лише з `{"type":"done"}` — показує прогрес лише поточного файлу. Обидва троттлять чергу (подія лише при зміні відсотка) — інакше 64КБ-чанки завалили б `_channel_queue`.

### _make_readonly_selectable — чому не state="disabled"
`state="disabled"` на `Text` блокує й виділення мишею (копіювання неможливе). Замість цього віджет лишається `state="normal"`, `<Key>` перехоплюється й блокується (`"break"`) для всього, крім навігації і Ctrl+C/A/Insert. Застосовано до консолі логів, "Довідки", `text_handshake`.

### text_out — реальний баг, знайдений користувачем
`text_out` спершу мав `state="disabled"` — виділення мишею мовчки нічого не копіювало, у буфері лишався порожній/старий вміст. Кнопка "Скопіювати в буфер" (`.get()` напряму) працювала коректно, але користувачі тягнуться до виділення мишею. Виправлено `_make_readonly_selectable`. (Кнопку згодом прибрано — "Згенерувати" копіює одразу.)

### Секція «Хендшейк» — одне поле, без перемикача ролі, ONE SESSION = ONE ROLE
Раніше перемикач ("Мій"/"Співрозмовника") давав змогу тримати обидва хендшейки одночасно — звідси реальний баг: `_session_key()` віддавав пріоритет `peer_key`, тож користувач, який спершу вставив чужий хендшейк, а потім натиснув "Згенерувати", бачив НОВИЙ власний код, а сесія/AES-пароль архіву й далі йшли зі старого `peer_key` — показаний код переставав відповідати реальному ключу каналу, і дві сторони могли розійтись у ключах непомітно. Перемикач прибрано; тепер щонайбільше ОДНЕ з `local_key`/`peer_key` будь-коли встановлене, `_session_key()` — без пріоритету (`local_key or peer_key`).

Один сеанс = одна роль. `_handshake_kind` (`_HANDSHAKE_KIND_MINE`/`_PEER`) — суто внутрішній прапорець (не UI), яке з двох гілок `_handle_verification_mismatch` застосувати; `_handshake_text`/`_handshake_fingerprint` — поточний (єдиний) вміст поля. Колишній перемикач замінено tooltip-ами на кнопках "Згенерувати"/"Вставити хендшейк" (пояснюють дію на наведення); підпису над полем більше немає — під полем лишається лише код підтвердження.

`_session_active()` — сеанс уже стартовано (ключ дериновано і/або канал встановлюється/встановлено). Натискання "Згенерувати" чи "Вставити хендшейк" (включно з тим самим повторно) при активному сеансі викликає `_confirm_reset_if_needed()` — `messagebox.askyesno` ("Почати новий сеанс?"); Ні — нічого не міняється; Так — `_reset_session_state()` (епоха, канал, обидва ключі, host/port, текст/код) і дія виконується далі. `_invalidate_session_if_active` (trace на пароль/ітерації/порт) використовує ту саму `_reset_session_state()`.

`_reset_session_state` — звільнення порту: `_channel_stop_event` (свіжий `threading.Event` на кожен скинутий сеанс) сигналізує ПОТОЧНОМУ `_channel_establish_worker` зупинитись; `establish_connection` реагує в межах `accept_poll_timeout_seconds` (0.5с), а не аж до `connect_timeout_seconds` (300с) — інакше старий listening-сокет тримав би `local_port`, і нова спроба на тому самому порту падала б "порт зайнятий". Застарілий потік (daemon) може ще секунди донести свою (вже нікому не потрібну) подію в чергу — вона позначена старим `epoch`, `_handle_channel_event` її ігнорує. Лишається вузьке (≤0.5с) вікно гонитви між `stop_event.set()` і фактичним `listener.close()` у старому потоці — якщо нова спроба стартує рівно в цей момент, можливий одноразовий "не вдалось з'єднатись" на тому самому порту; повторне натискання кнопки вирішує (порт до того часу вже вільний). transport.py не змінено — `establish_connection` вже приймала `stop_event`, appearance.py просто починає ним користуватись.

Порожня парольна фраза при "Згенерувати"/"Вставити" — не попередження, а `_prompt_passphrase()`: модальне віконце (маскування як у `entry_passphrase`, чекбокс "Показати", Enter=OK, Esc/хрестик=Cancel); OK з непорожнім значенням → `var_passphrase.set(...)` → дія продовжується. `var_passphrase` має trace (`_invalidate_session_if_active`) — виклик `set()` тут стається ДО деривації ключа (`peer_key`/`local_key` ще `None`), тож `_session_active()` у трейсі — `False`, нічого не скидається; це навмисний інваріант, не збіг.

`kind == "verification_failed"` — той самий діалог-помічник: пояснення + поле з поточною фразою. Повтор — на ТОМУ САМОМУ хендшейку, пересилати нічого не треба (`_retry_after_mismatch`). Раніше MINE перегенеровував (новий salt → новий ключ), а PEER переобробляв СТАРИЙ текст — ключі не могли зійтись ніколи. Тепер:
- MINE: salt/sid/iterations/текст лишаються, `local_key` переводиться з нової фрази, код оновлюється, знову слухає (новий epoch/stop_event).
- PEER: переобробляє збережений текст, знову конектиться; якщо інша сторона ще не натиснула OK — connect-цикл чекає до таймауту, статус пояснює.
- Фраза міняється з `_suppress_param_invalidation=True` — trace не робить повне скидання; скидається лише спроба каналу (`_reset_channel_attempt`: epoch, stop_event, сокет, channel_key, прапорці, AES-архів). Ручна зміна фрази/ітерацій/порту поза діалогом — повне скидання, як і раніше.
- Cancel: MINE слухає далі з поточною фразою — помилка могла бути в іншої сторони, її виправлений повтор має до кого підключитись; діалог знову з'явиться лише якщо інша сторона підключиться. PEER — не конектиться (інакше Cancel з обох боків зациклив би діалоги), статус: "вставте хендшейк ще раз".
- Лише `VerificationError` → `verification_failed`; будь-який інший виняток `verify_channel` (обрив/таймаут, `ConnectionFailed`) → `connection_failed`, текст помилки — у статусі каналу, без діалогу.
- Діалог під час іншого модального (`_modal_depth>0`, напр. "Почати новий сеанс?") відкладається (подія повертається в чергу); якщо epoch змінився, поки діалог був відкритий, — результат ігнорується.

AES-архів і ключ каналу: пароль архіву — `_session_key()` на момент "Ініціалізувати передачу", тож після повтору/нового сеансу він може відрізнятись від `channel_key`. `_transfer_archive_key` запам'ятовує ключ архіву; "Надіслати" активна лише при `hmac.compare_digest(_transfer_archive_key, channel_key)`. Будь-яке скидання спроби видаляє такий архів (файл застосунку в `pack_subdir_name`) і просить ініціалізувати передачу заново; незашифрований payload лишається.

Вставка: текст з'являється в полі лише після успішного `_parse_incoming_handshake` (host/port 1..65535 перевіряються ДО запису стану) — скопійована помилково фраза не показується незамаскованою.

Ctrl+V у полі `text_handshake` == кнопка "Вставити хендшейк" (без змін).

### _receive_worker (appearance.py) — цикл, не одноразовий виклик
`receive_files()` викликається в циклі до `PeerClosed` — щоб один канал міг прийняти кілька передач за сеанс. Підтверджено E2E: після прийому від A, той самий канал з боку B надсилає файл назад до A.

### _receive_worker / _send_worker / _channel_establish_worker / _connection_setup_worker — широкий except Exception
Знайдено code-ревʼю: воркери ловили лише очікувані типи (`TransportError`/`PeerClosed`, `ConnectionFailed`/`VerificationError`, `UpnpError`/`StunError`). Побитий кадр (`KeyError`), зниклий файл (`FileNotFoundError`), побита XML-відповідь (`ET.ParseError`) — тихо вбивали потік, GUI лишався заморожений без повідомлення. Тепер кожен воркер додатково ловить `except Exception` і кладе подію-помилку в ту саму чергу.

### receive_error / receive_closed — канал позначається розірваним
Раніше `_handle_channel_event` лише логував ці події, `channel_verified` лишався `True` — статус і далі показував "Підтверджено", хоча прийом уже неможливий. Тепер обидва випадки виставляють `channel_verified = False`, оновлюють статус і викликають `_update_send_button_state()`.
